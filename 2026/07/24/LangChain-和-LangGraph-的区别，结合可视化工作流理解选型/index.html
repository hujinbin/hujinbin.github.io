LangChain 和 LangGraph 的区别，结合可视化工作流理解选型

准备做一个 AI 应用时，经常会遇到这个问题：已经能用模型 SDK 发请求了，还需要 LangChain 吗？如果接下来有多个步骤，是不是就应该直接上 LangGraph？

只用“简单任务选 LangChain，复杂任务选 LangGraph”来判断，信息还不够。一个步骤很多但顺序固定的任务，可能用普通函数就能维护；一个看似简单的“查到合适资料再回答”，却可能需要模型反复选择工具。两种复杂性并不一样。

更有用的判断依据是：谁决定下一步，哪些数据需要保留，任务中断后要怎样继续。 本文沿着这三个问题比较两者，并结合 GitHub 上的 LangChainWeb，说明可视化编辑与运行编排之间的关系。

一、先把模型组件、Agent 和图运行时分开

LangChain 既提供消息、模型、工具等组件，也提供 createAgent 这样的高层代理入口。使用模型组件，和使用一个能够选择工具的 Agent，是两种不同的用法。

LangGraph 则提供有状态任务的编排机制。开发者明确描述状态、处理节点和路由规则，可以把普通业务逻辑、模型调用或代理放进一张图中。

层次 主要解决什么 应用需要描述什么
LangChain 组件 怎样组织模型输入、调用与输出 消息、模板、模型配置、解析与校验
LangChain Agent 怎样运行模型与工具之间的决策循环 任务要求、可用工具、行为规则与边界
LangGraph 怎样组织状态和执行路径 节点职责、字段更新、依赖、路由与恢复方式

LangChain 的 Agent 建立在 LangGraph 之上。因此，“使用 createAgent”与“直接编写图”更像是在选择暴露多少控制点，而不是选择两套完全不相干的技术。LangChain 官方概览说明了这一关系。

反过来，LangGraph 节点也可以调用现有 SDK、HTTP 服务或普通函数，不要求所有能力都先改造成 LangChain 组件。它提供的是执行组织方式，具体节点做什么由应用决定。LangGraph 官方概览介绍了这一定位。

另外还存在一个合理选择：继续使用现有 SDK 和异步函数。如果输入输出稳定、步骤清楚、维护成本可控，就可以等具体问题出现后再引入抽象。

二、三个问题决定你需要哪层能力

1. 下一步是谁决定的

“先生成提纲，再写正文”是开发者确定的路径。“先搜索一次，发现信息不足，再换关键词继续搜索”则可能需要模型参与下一步决策。

但只在分类节点中用了一次模型，不代表整个流程就变成了自主 Agent。例如，模型只允许输出“退款、开票、普通咨询”，之后按固定规则处理，仍然是一套预先设计的工作流。

判断时要看运行时的决策权：模型是在完成一个受约束的步骤，还是在反馈循环中决定使用什么工具、继续多少步以及何时结束。官方的工作流与代理说明对此有进一步讨论。

2. 中间数据需要保留到什么程度

如果页面只要最终的一句摘要，函数局部变量就可能够用。若用户需要分别查看提纲、正文、检查意见，并且从某个阶段继续，状态就应成为显式的数据结构。

这也不是“LangChain 没有状态，LangGraph 才有状态”。Agent 本身就会处理消息等状态。区别在于，现成的状态模型是否满足任务，以及开发者需要怎样控制每个字段的更新。

3. 中断后需要怎样继续

如果失败后从头生成一段短文本即可，恢复机制可以比较简单。若任务已经提交媒体生成、等待人工确认，或者跨越较长时间，就需要认真设计检查点、任务标识、恢复入口和副作用处理。

三、沿着一个文章工具的变化看选择

相比一次比较所有功能，把同一个产品逐步增加的需求写清楚，更容易看出引入框架的时机。

阶段一：根据主题生成一份摘要

需求是用户输入主题，页面展示一段回答。一个模型 SDK 加输入校验、超时和错误处理，就能形成完整功能。

此时引入 LangChain 的理由可以是统一模型接口、复用已有组件，而不是“AI 项目必须使用框架”。如果只是固定接入一个服务，增加适配层是否划算，要看团队维护成本。

阶段二：提纲、正文和改写共享组件

功能增加后，几个入口都需要组织固定规则、历史消息和输出格式。重复逻辑开始分散，提示模板和模型适配也需要统一维护。

这时 LangChain 组件的价值更明显：把输入准备、调用、解析分开组合，让它们可以独立替换和检查。具体模型是否支持工具调用或结构化输出，仍要单独确认。相关接口可以参考模型文档。

如果提纲和正文仍然只有固定的前后关系，用普通异步函数串联这些组件也可以，不必立即构建复杂的图。

阶段三：支持并行配图、检查与人工确认

现在，正文和封面需要独立生成，发布前必须检查内容并等待用户确认。用户还希望看到每个阶段的结果，确认后从指定位置继续。

这时需要表达的已经包括依赖、状态合并、暂停和恢复。可以评估用 LangGraph 组织这些关系：哪些节点能同时开始，汇总需要哪些结果，检查不通过走哪里，确认信息如何回到对应任务。

代价也会随之增加。开发者需要维护状态结构、图版本、存储和恢复行为，还要处理旧任务在流程升级后能否继续执行。

阶段四：让资料收集环节自主使用工具

如果用户要求“围绕主题收集足够资料，再形成提纲”，资料收集可能需要多次搜索、读取和比较。工具使用次数与顺序不一定事先固定，可以评估 LangChain Agent。

整条业务流程仍然可以由显式图管理，只把“收集资料”作为包含 Agent 的局部步骤。这样，模型在允许的工具范围内探索，后续的编辑和人工确认仍遵循明确规则。

Agent 带来的实现工作还包括工具参数校验、允许的操作范围、调用次数与时间预算，以及工具失败后的处理方式。高层入口简化了循环组织，但不会替应用决定这些约束。Agent 文档介绍了模型与工具循环的配置方式。

四、把收益和需要承担的工作一起比较

选择 适合解决的问题 得到的便利 仍需承担的工作
直接 SDK / 普通函数 少量稳定调用、清楚的固定步骤 依赖少，行为容易追踪 自己统一消息格式、错误与复用逻辑
LangChain 组件 多处复用模板、模型和解析过程 调用约定更一致，组合更方便 检查适配器能力，维护业务校验
LangChain Agent 模型根据工具反馈持续决定动作 复用现成决策循环与扩展入口 工具设计、行为约束、预算和质量评估
直接使用 LangGraph 需要显式管理分支、状态或恢复 执行结构清晰，控制点更充分 状态协议、路由、存储、恢复及版本兼容
LangGraph 中组合链或 Agent 固定流程里包含局部动态决策 不同环节可以使用合适的抽象 明确子任务边界，统一状态和错误约定

这里没有按“能力强弱”排列。更高层的入口可能减少样板工作，更直接的图编排则允许精细控制。是否值得多承担这些控制点，应由当前需求决定。

迁移也不一定要重写全部业务。先把一个步骤的输入、输出和错误约定固定下来，未来可以把它放进普通函数、调用链或图节点。稳定的边界，比尽早选定所有框架更有助于后续调整。

五、可视化画布与执行器分别负责什么

在前端项目里，看到节点和连线，很容易以为“已经有了 LangGraph 工作流”。实际上，编辑器首先表达的是一份可修改的业务定义。

可以把相关数据分成三个层次：

层次 关心什么 举例
编辑器状态 用户正在怎样编辑 选择、拖拽、缩放、撤销
流程定义 任务应该怎样执行 节点类型、参数、输入绑定、依赖
运行状态 某次任务已经执行到哪里 本次输入、节点输出、错误、待确认事项

React Flow 负责画布交互，并不会自动把可见连线编译成 LangGraph。应用需要把画布转换成受校验的定义，再由执行层赋予节点和连线具体含义。即使采用其他执行器，也可以复用同样的前端定义。

从公开项目观察这些边界

GitHub 上的 LangChainWeb 提供了可视化编辑器的前端实现。以下引用固定到本文查看的公开提交，可以重点观察三个位置：

公开实现入口 可以借鉴的设计 对选型的启发
工作流编辑器 在画布节点与业务节点之间转换，运行前先保存 UI 数据结构与执行协议可以分开演进
画布状态管理 管理图快照、撤销和未保存状态 编辑历史与图执行检查点承担不同职责
对话助手 比较请求前后的编辑版本，保留候选生成结果 模型输出进入产品前仍需交互控制

例如，模型生成草稿期间，用户可能已经手动修改了画布。比较编辑版本后再决定应用或保留候选结果，可以避免慢响应覆盖新内容。这类问题需要前端状态设计，选择哪套模型框架都不会自动解决。

模型生成流程草稿与执行草稿，也是两个阶段。设计阶段可以使用一次受约束的结构化生成；运行阶段再按保存的定义调度。仅从“能对话生成节点”这一功能，无法判断运行时是否存在自主 Agent 循环。

这个公开仓库适合学习前端实现。完整的模型调用、任务调度与持久化能力，需要通过配套服务或自己的适配接入，不能从前端依赖或画布外观推断已经具备哪些服务端能力。

六、这些能力需要落实到具体配置

选型时容易把框架“支持某项能力”，理解成“安装后已经拥有这项能力”。下面几个问题尤其需要在原型中核实。

有状态，不等于已经持久化

图运行时存在 State，说明步骤之间能够传递数据；跨请求或跨进程恢复，则需要检查点存储和相应的调用约定。自托管场景下，要配置 checkpointer，并正确使用线程标识。LangChain Agent 同样可以接入这些底层能力，无须因为需要记忆就立即重写为自定义图。持久化文档解释了检查点与长期存储的区别。

图上有分支，不等于获得了并行收益

两条支路如果都读取前一步结果、互不依赖，才有并行机会。即使调度器支持并发，应用中的队列、锁、模型限流和共享资源也可能让实际调用排队。

理想情况下，并行部分的等待时间受较慢支路影响，但整项任务还包含串行步骤、排队和汇总开销。应观察实际运行记录，不能只根据图里画了几个分支就估算性能提升。

可以恢复，不等于外部操作只执行一次

检查点帮助恢复图状态，但已经发送到外部系统的请求，还需要任务标识、幂等和结果查询。人工中断恢复时，包含中断的节点会重新进入，中断前的普通代码可能再次执行。这个边界应按官方中断规则设计。

能逐步返回消息，不等于页面已有实时反馈

模型文字片段、图状态更新、节点事件，是不同的信息。服务端需要把选定事件传给客户端，页面也需要按任务和节点正确归属。如果中间步骤必须等完整结果才能处理，还可能影响展示时机。流式输出文档列出了可以消费的信息类型。

这些都是原型需要验证的具体工作，不能只在技术方案里勾选“支持”就结束。

七、用一个小原型完成选型验证

比较之前，先选同一项代表性任务，固定输入、模型配置和结果要求。否则，一边只生成一句回答，另一边搜索多轮再生成正文，得到的耗时和费用没有可比性。

除了正常结果，可以加入以下验证：

验证场景 需要观察什么 它帮助判断什么
同一输入重复运行 输出质量、模型调用次数、耗时与用量 业务质量是否稳定，开销是否符合预期
某个工具暂时失败 重试范围、错误定位、是否重复副作用 高层循环是否满足现有错误处理需求
一个并行节点变慢 汇总何时开始、结果是否完整 依赖与合并语义是否正确
人工确认前重启进程 能否找到原任务并正确恢复 存储与恢复机制是否真正接通
生成期间修改画布 旧响应是否覆盖新编辑 前端状态边界是否清楚
更新流程定义后查看旧任务 能否识别当时的配置与状态 版本管理是否足以支持维护

这些是验证方案，不是对某个框架的性能测试结论。对需要模型决策的任务，还应记录工具选择和结束原因；对固定工作流，则重点检查每个阶段的输入输出以及失败路径。

依赖和部署条件也要在这个阶段确认：所选版本的运行环境要求、已有模型适配是否覆盖必要能力、检查点存储是否可用，以及升级后能否继续读取历史任务。不要把某个项目自己的兼容方案当作框架的通用能力。

如果当前最麻烦的是模型接入重复，就先统一组件；如果是工具决策循环，可以先评估 Agent；如果是状态和控制流难以维护，再设计显式图。也可以让不同业务模块保留不同的实现，只在交界处统一数据约定。

想把这些原则放到可编辑产品中观察，可以到 GitHub：hujinbin/LangChainWeb 查看公开实现。欢迎 Star，或者通过 Issue 交流画布交互、流程协议和 AI 应用的实现思路。
